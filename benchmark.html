Under the hood

Two databases, one question at a time.

How ResaleWise splits the work between PostgreSQL and MongoDB, how we check that the two agree, and how fast each one answers exactly the same question.

Architecture

Each database does what it is best at

PostgreSQL · relational

  • 985,219 sales in 5 normalised tables (towns, flat types, models, blocks, transactions)
  • Accounts and the shortlist: users ↔ transactions many-to-many through bookmarks
  • CHECK constraints, foreign keys, NOT NULL, a BEFORE UPDATE and an AFTER INSERT/UPDATE/DELETE trigger
  • Views and three materialized views of precomputed medians; window functions (RANK, RANGE frames)
  • PostGIS: block locations, stations, distances (the cross-check)

MongoDB · documents

  • Reviews: free text and tags, a $jsonSchema validator, a text index, $facet summaries
  • Stations as GeoJSON MultiPoints (one point per exit), blocks and amenities as Points, with 2dsphere indexes
  • $geoNear finds every block’s nearest station; the results flow back to PostgreSQL
  • A denormalised copy of the sales, so both engines can be timed on the same data

Data flow: HDB CSV → PostgreSQL (scripts/load.py) → OneMap geocoding → MongoDB blocks_geo + places → $geoNear → PostgreSQL block_features → price-driver analysis. Every distance is recomputed in PostGIS and compared.

How the timings were taken

A fair test, written down before the numbers

Same answers first

  • Every query is run on 20 parameter sets and the results are compared before anything is timed.
  • Three set-ups: PostgreSQL as the app uses it (joins), PostgreSQL with one flat table, and MongoDB. The flat table separates the data-model effect from the engine effect.
  • Matching indexes on both sides (Equality → Sort → Range order).

Then the clock

  • Fixed random seed; the same parameters replayed for each set-up, in rotating order.
  • Warm-up runs discarded; median, p95, p99 and a bootstrap 95% interval for the median.
  • Throughput at 1, 2, 4 and 8 threads, connections opened before the clock starts; query plans from EXPLAIN ANALYZE and explain("executionStats").
  • Single-row writes timed twice: once waiting for the disk on both engines, once not, so both make the same promise.
